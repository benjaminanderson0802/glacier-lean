## Upload result and limits

The installed `markitdown==0.1.8` package reported its optional PDF reader dependency missing. No dependency or product code was changed for this measurement.

Both model runners remained loaded in Ollama from the preparatory smoke run during the three-repeat run. ## Follow-up

Measured the backend process itself with a temporary `GLACIER_HOME`: after `/api/health` answered, `/proc/<backend-pid>/status` reported `VmRSS: 134076 kB` (130.9 MiB). This agrees with the original report's separate idle backend value (130.4 MiB). The roughly 1,600 MiB values in the automation table are **combined peak backend + Ollama runner RSS**, not backend idle RSS; the JSON samples show about 139 MiB backend plus 1,470 MiB Ollama runner.

`python -X importtime -c 'import app'` showed `markitdown` imported during app startup (about 222 ms cumulative), along with `magika` and `onnxruntime`. Separate fresh-process RSS samples after a single import were: FastAPI 39,412 KiB; DBOS 65,036 KiB; sqlite-vec 27,024 KiB; MarkItDown 65,604 KiB; Magika 47,572 KiB; ONNX Runtime 44,476 KiB. The app's health-ready RSS is lower than the single-import totals because these process measurements are not additive and overlap shared runtime pages. DBOS remains an expected startup dependency for durable runs. Document conversion now imports MarkItDown only when a document is read; startup tests assert that importing `app` leaves MarkItDown, Magika, and ONNX Runtime absent from `sys.modules`.

Classification diagnosis: the raw light-model replies were numbered/bulleted category lists and omitted a final item once; the original `list_items` check accepts those list markers, but required an exact ten-line list and an exact label. The standard model returned ten entries but labeled the ninth message (`How do I change my billing date?`) as `sales`, while the benchmark expected `billing` without giving category rules. That category was ambiguous. The prompt now defines explicit rules and that billing-date case, and the local AI step can constrain every label in a JSON array to the supplied choices. On this host, real Ollama trials with that prompt/schema gave qwen3:0.6b the exact expected ten labels (10/10), while granite3.3:2b still mislabeled the first app-crash message as billing (9/10). These raw trials diagnose the change; the original three-repeat figures above remain unchanged and are not re-scored.

Acceptance evidence for the follow-up: backend tests `test_importing_app_does_not_import_document_conversion_stack`, `test_choose_one_sends_json_enum_and_returns_selected_option`, and `test_choose_one_rejects_malformed_model_reply`; benchmark test `test_classification_task_has_clear_rules_and_constrained_labels`. Focused checks passed (22 passed in 2.51s). Full locked backend suite: `468 passed, 1 skipped, 1 warning in 511.27s (0:08:31)`.
